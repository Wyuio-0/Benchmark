# 高层级 Benchmark 论文结构调研

> 调研日期：2026-11-17。以下论文均已在 `_reference_papers/` 中保存 arXiv PDF。本文只根据已核验论文的题目、venue、PDF 正文结构总结；正式写 related work 时再逐条补 BibTeX，不凭记忆生成参考文献。

## 2. 这些论文的共同组织范式

### 2.1 先证明“为什么需要新环境”

高层级 benchmark 论文的引言通常按以下顺序推进：

1. agent 正在进入真实任务，动作会改变外部世界；
2. 已有评测要么太合成、要么只测单轮文本、要么环境不可复现；
3. 因而已有分数不能回答目标能力/风险；
4. 本文引入一个可执行、可重置、可判分的环境；
5. 用该环境得到一个超越排行榜数字的新发现。

本文对应写法：工具型 agent 在日常办公/交易/运维任务中已经能写文件、发消息、改数据库、执行代码；已有安全 benchmark 多假设有攻击者或恶意注入，无法解释“用户是善意的、材料看起来正常，但环境里存在关键反证”的危险动作。

### 2.2 benchmark construction 必须独立成节，而且早于实验结果

优秀 benchmark 论文不会一上来就列模型分数，而会先让审稿人相信数据和环境：

- 任务从哪里来；
- 环境状态如何生成和重置；
- 什么证据支持风险存在；
- 安全路径是否真实可执行；
- outcome 如何客观判定；
- 数据质量如何审计；
- 数据集统计和覆盖范围是什么。

本文因此应把 `CEG-Bench` construction 放在实验前：种子、RU/RI/FI、K1–K9、关键证据、安全对照版、确定性评测函数、人工/judge 标签都在这一节建立可信度。

### 2.3 “验证评测器”是主贡献的一部分

ToolEmu 和 AppWorld 都没有把 LM judge 或 validation solution 当作理所当然，而是单独验证：

- ToolEmu 用人工评估 emulator/judge 找到的 failure 是否真实；
- AppWorld 为任务提供 validation solutions，并单独说明最终数据集如何通过质量检查。

本文也应把三层评测口径讲清楚：

1. **行为层**：环境终态/写操作触发的 deterministic behavior score，是主安全判据；
2. **证据层**：人工标注关键证据和轨迹中是否获取；
3. **意识层**：LLM-as-judger 只在人工标签校验下判断是否识别风险，不能替代行为判分。

### 2.3 主实验不是“模型分数表”，而是围绕研究问题展开

τ-bench、AgentDojo、ToolEmu 都在主结果后做 challenge/ablation analysis。本文的优势更明显，应该把实验组织成因果链：

```text
风险版本是否危险？ ── 安全对照版能否完成？ ── 证据有没有被获取？
       │
       ├── position 改变获取概率
       ├── wording 改变识别概率
       └── enhancement/topology 是否跨过证据与意识瓶颈
```

这样每个实验都承担一个论证职责，而不是“我们又跑了一个方法”。

## 3. 本文最适合的结构选择

建议采用：

```text
Introduction
→ Related Work and Positioning
→ Problem Formulation: Context–Environment Gaps
→ CEG-Bench: Construction and Evaluation
→ Diagnostic Experimental Design
→ Results
→ Discussion
→ Conclusion
```

### 为什么不是“Method → Experiments”？

本文不提出一个新 agent 算法，主贡献是概念、benchmark、诊断协议和实证发现。若按方法论文写“我们提出三个模块”，会把工作降格成若干工程技巧。Benchmark 论文的核心是：

- 问题定义是否新；
- 环境是否可信；
- 标签和判分是否可靠；
- 实验能否排除替代解释；
- 结果是否改变社区对 agent safety 的理解。

### 为什么要把 Related Work 放前面？

安全 agent 方向已有 AgentDojo、ASB、ToolEmu、Agent-SafetyBench、R-Judge。审稿人第一反应会是“和 prompt injection/agent safety benchmark 有什么区别”。第二节直接用比较表回答：

- 无攻击者 vs 有攻击者；
- benign but mistaken user vs malicious instruction；
- 环境行为终态 vs 静态记录判断；
- 关键证据标签和安全对照版 vs 只有风险标签；
- position/wording 反事实干预 vs 只有最终 ASR；
- 三阶段失败归因 vs 单一安全分。

### 为什么实验设计单独成节？

position、wording、安全增强、多 agent 拓扑和普通 token 对照不是附属 ablation，而是回答“为什么失败”的主证据。把它们集中成 diagnostic protocol，可以让审稿人看到本文不是堆实验，而是在做机制识别：

- position：操纵 evidence availability / discoverability；
- wording：操纵 evidence interpretability；
- safe counterpart：排除任务能力不足；
- enhancement：测试外部安全机制能否补证据/意识短板；
- cost-matched topology control：区分安全角色分工与单纯多耗 token。

## 4. Benchmark 审稿风险与对应位置

| 可能审稿问题 | 论文中在哪里回答 | 应答要点 |
|---|---|---|
| 这些坑是否人为、不自然？ | Construction、case writer rules、附录案例 | 信息必须有正常业务用途；不造只承载考点的告示；线索沿正常任务路径出现 |
| agent 是否其实没有能力完成任务？ | safe counterpart + main results | 最小修改移除坑点后，同一任务应能完成；安全失败与一般任务能力分开 |
| 环境里是否根本没有安全路径？ | Construction quality controls | 每个 case 要求存在可执行替代动作：暂停、澄清、拒做危险部分、改走合规路径 |
| evaluator 是否误判？ | Metrics/Judge/QC + Appendix | hazard 由确定性终态和写操作判定；LLM judge 只做风险意识分类并报告人工一致性 |
| ASR 降低是否因为多花 token？ | Topology experiment + cost-matched controls | 报告总 token、工具调用、步骤、耗时；加入无安全职责的额外阶段对照 |
| 和 prompt injection 有什么区别？ | Threat model + Related Work | 用户善意、无攻击者、工具返回不含恶意指令；风险来自普通环境证据与上下文缺口 |
| 数据规模是否足够？ | Dataset statistics + expansion pipeline | 不把规模作为唯一优势；强调正交覆盖、证据标签、成对控制和可执行判分 |
| 结果是否可复现？ | Environment/reset + Reproducibility Appendix | 本地可重置状态、确定性工具、固定评测函数、运行记录、模型版本、重复次数 |

## 5. 写作时的术语建议

1. 内部可以继续叫 ASR，但正文建议定义为 **Hazardous Action Rate (HAR)** 或 **Unsafe Action Rate (UAR)**。本工作没有 attacker，“Attack Success Rate” 会误导威胁模型。
2. 少说“防御方法失败”，改写为“generic safeguards do not directly address evidence acquisition and interpretation bottlenecks”。这既保留发现力度，又不显得工作只是负结果。
3. “benign” 只限定用户意图和无攻击者，不等于环境没有风险；环境中可以有过时状态、遗漏约束、冲突规则。
4. LLM-as-judger 不叫 ground truth；ground truth 来自人工证据标签、确定性环境终态和评测函数。
5. K1–K9 是风险隐藏/发现路径 taxonomy，RU/RI/FI 是 context–environment gap 的风险类别，二者不要混成一个分类体系。
