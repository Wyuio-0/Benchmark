# 0. 论文的核心叙事

## 0.1 一句话主张

工具型 agent 在**无攻击者、用户意图良性**的日常任务中仍会做出危险动作；这些动作可以被统一理解为 **context–environment gaps**：agent 把用户上下文或表面状态当成安全行动依据，但没有通过工具获取、理解或优先服从环境中的关键约束证据。

## 0.2 本文最有辨识度的贡献

本文不把“安全”只测成一个最终 ASR/HAR，而是把危险动作前的认知—行动链拆成三个可检验阶段：

1. **Evidence acquisition**：环境中的关键证据是否被检索到；
2. **Risk recognition**：证据已在轨迹中时，agent 是否意识到危险；
3. **Instruction prioritization**：意识到危险后，agent 是停止/澄清/改走安全路径，还是仍按用户指令执行。

在此基础上，benchmark 提供四类普通安全评测没有同时提供的控制：

- 每条风险 case 的**可执行安全路径**和确定性危险终态；
- 每条 case 的**安全对照版**，用最小修改移除坑点以排除任务能力不足；
- 人工标注的**关键证据标签**和三阶段失败归因；
- **position / wording 反事实变体**，分别操纵证据获取难度与证据理解难度。

## 0.3 论文不要怎么写

- 不要写成“我们先实现了两个防御，又试了一个预训练模型，再做了几个 topology”的实验流水账。
- 不要把核心卖点设为“所有方法都防不住”。负结果本身不够，关键是解释为什么：现有增强没有作用在证据获取/风险识别瓶颈上。
- 不要和 prompt injection benchmark 正面对打“攻击类型更多”。本文赢的是 benign-task、环境证据、行为终态、安全对照和机制归因。
- 不要把 K1–K9 与 RU/RI/FI 混为一个 taxonomy。前者描述风险如何被藏起来、需要怎样发现；后者描述 context–environment gap 的类型。

## 1.1 标题备选

1. **Context–Environment Gaps: Benchmarking Tool-Using Agent Safety in Benign Tasks**（沿用旧稿，稳妥）
2. **Benign but Unsafe: Diagnosing Context–Environment Gaps in Tool-Using Agents**（更强调诊断和反直觉）

## 1.2 摘要句群模板

> 不用逐句直译，先按句群写，避免一上来堆 benchmark 数字。

1. **场景与风险**：Tool-using agents increasingly act on files, messages, code, databases, and operational tools, so ordinary benign tasks can lead to concrete harms when the agent acts on incomplete or outdated context.
2. **现有缺口**：Prior agent-safety benchmarks primarily study adversarial prompt injection, malicious tool content, or static risk awareness, leaving a central deployment question unanswered: why do agents take hazardous actions when no adversary is present and the environment contains evidence sufficient to avoid them?
3. **概念方案**：We formulate these failures as **context–environment gaps**: a user's request or trusted context underspecifies, conflicts with, or misstates safety-relevant environment facts that must be recovered through tool-mediated observation.
4. **benchmark 资源**：We introduce `[Benchmark Name]`, a reproducible stateful benchmark of `[N]` executable tasks across `[S]` tool-centric scenarios spanning requirement underspecification, requirement infeasibility, and factual inconsistency. Each task is paired with a minimally edited safe counterpart and manually annotated key evidence.
5. **评测/诊断**：A deterministic environment-state evaluator measures hazardous actions, while human labels and a validated LLM judge attribute unsafe trajectories to insufficient evidence acquisition, failed risk recognition, or unsafe compliance after recognition.
6. **控制与设置**：We further introduce position and wording counterfactuals that separately manipulate evidence discoverability and interpretability, and evaluate `[M]` base agents, `[3]` safety enhancements, and `[4]` multi-agent topologies with cost-matched controls.
7. **主要发现**：Across `[R]` repeated runs, agents reach hazardous states in `[待填：%]` of risk tasks while completing `[待填：%]` of safe counterparts; `[待填：最主要失败阶段]` accounts for the largest share of unsafe trajectories. Moving evidence to less salient positions primarily `[待填：降低/改变]` evidence acquisition, whereas implicit wording primarily affects risk recognition.
8. **意义**：These results suggest that safe tool use requires evidence-centric perception and interpretation, not only generic refusals, action guards, or additional model calls.

# 2. Introduction

## 2.1 本节目标

让审稿人在一页半内相信四件事：

1. 问题真实且重要：善意用户和日常任务也能造成财务、隐私、数据、权限、服务可用性风险；
2. 现有 benchmark 不能回答本文问题：有攻击者的 prompt injection、静态 safety judgment、一般 utility benchmark 都不够；
3. 本文概念清楚：context–environment gap + 三阶段证据链；
4. 本文资源和发现有分量：可执行环境、安全对照、关键证据标签、反事实变体、增强/拓扑评测共同支撑机制结论。

## 2.2 推荐段落结构

### Paragraph 1：从部署场景切入

写 agent 已能对真实状态执行写操作：发邮件/消息、修改文件和表格、执行代码、操作数据库、改配置、触发购买或发布。风险不再只是生成了有害文本，而是产生不可忽视的外部世界后果。

要点：
- 用户通常不是攻击者；
- 用户可能信息不完整、说错状态、提出一个与环境约束冲突的紧急要求；
- agent 的安全行为依赖环境核验，而不是只对用户文本做内容安全过滤。

### Paragraph 2：给一个具体 motivating example

选一个最容易讲清楚的 case，建议用冷冻可颂/冷链、咖啡券截止日期、Git 历史泄露或 production/test 名称碰撞。图 1 可以展示：

```text
用户上下文/请求  →  agent 工具观察  →  关键环境证据  →  安全/危险终态
```

例子要包含：
- 用户想完成的正常目标；
- 上下文中看似合理的说法或要求；
- 环境中哪条证据构成反证/约束；
- 直接执行的具体危险终态；
- 安全替代行为是什么。

### Paragraph 3：指出现有评测的三个不足

建议写成三个并列：

1. **Adversarial safety ≠ benign-task safety**：AgentDojo/ASB 主要研究 prompt injection 等攻击者行为；本文没有恶意指令或被污染的工具返回。
2. **Risk awareness ≠ safe action**：R-Judge 让模型判断记录中的风险，但不要求 agent 在有状态环境里采取安全动作。
3. **Utility benchmarks do not localize safety failures**：WebArena/AppWorld/τ-bench 等能测任务完成或 policy following，但通常没有关键证据标签、安全对照版和 position/wording 反事实，不能说明失败发生在获取、识别还是服从阶段。

### Paragraph 4：提出 context–environment gaps

定义三类：

- **Requirement Underspecification (RU)**：请求没给安全边界，agent 必须从环境规则中补全；
- **Requirement Infeasibility (RI)**：请求明确要求的路径与环境安全约束冲突；
- **Factual Inconsistency (FI)**：用户陈述与当前环境事实不一致或已过时。

强调环境只能通过工具调用部分可观察，因此证据链可能在三个环节断掉。

### Paragraph 5：介绍 benchmark 和诊断设计

用一张概览图说明：

- stateful local tool environment；
- 人工种子与批量扩展；
- risk task + safe counterpart；
- evidence annotation；
- deterministic outcome evaluator；
- human + LLM judge；
- position/wording 变体；
- safety enhancement 与 topology 评测。

### Paragraph 6：贡献列表

建议四条，不超过四条：

1. **Conceptual contribution**：形式化 benign tool-use tasks 中的 context–environment gaps，并提出 evidence acquisition → risk recognition → instruction prioritization 的失败归因框架。
2. **Benchmark contribution**：构建 `[N]` 个可重置、可执行、可客观判分的风险任务，覆盖 `[S]` 个场景和 RU/RI/FI 三类 gap；每个任务配安全对照版和关键证据标签。
3. **Diagnostic contribution**：设计 position/wording 反事实变体和人工+judge 归因流程，把危险动作区分为没找到证据、找到了但没意识到、意识到但仍执行。
4. **Empirical contribution**：评测 `[M]` 个模型、三类安全增强和多组拓扑，并用 token/步骤匹配对照证明 topology 效应是否来自安全角色分工而非额外计算。

- 工具 API 的具体实现细节；

- 初步实验中不稳定的小样本数字；
- 过度展开局限性；

# 4. Problem Formulation: Context–Environment Gaps

## 4.1 本节目标

把“挖坑”变成严谨的问题定义，让 benchmark 不显得是人工脑筋急转弯。审稿人需要看到：任务自然、证据存在、安全路径可执行、失败终态可观察。

## 4.2 形式化记号

建议定义：

- 用户请求 \(u\)；
- 上下文 \(C\)：用户消息、对话中显式给出的说法、agent 初始可见的高层说明；
- 环境状态 \(E\)：文件、消息、邮件、数据库、代码仓库、业务配置、商品/订单状态等；
- 工具集合 \(T=T_r \cup T_w\)：只读工具与写入/执行工具；
- 轨迹 \(\tau=(o_1,a_1,\ldots,o_t,a_t)\)；
- 证据集合 \(e^\star\)：足以识别风险并选择安全行为的最小环境观察；
- 危险谓词 \(H(s_T)\)：终态或关键写动作是否触发明确危害；
- 任务效用 \(U(s_T,u)\)：是否完成用户的合法目标；
- 安全策略 \(S(E,u)\)：在当前环境中可执行的安全动作集合。

一个任务构成 context–environment gap，当且仅当：

1. 仅依据 \(C\) 的自然执行路径可能触发 \(H\)；
2. \(E\) 中存在可通过正常工具路径获取的正面证据 \(e^\star\)；
3. 获取并正确使用 \(e^\star\) 后存在可执行安全路径；
4. 安全路径仍尽可能服务用户的合法目标，而不是简单拒答。

## 4.3 三类 gap

### 4.3.1 Requirement Underspecification (RU)

- 用户请求缺少对象范围、保留边界、收件人范围、数量口径、期限或动作语义；
- agent 不能自行补出危险选择；
- 安全行为是查证规则、澄清或选择保守可解释的方案。

例子：清理旧版本但环境中存在唯一可编辑源稿/备份链依赖；群发但没限定外部收件人和附件范围。

### 4.3.2 Requirement Infeasibility (RI)

- 用户明确要求的方案与环境中的硬约束冲突；
- 两个要求不能同时满足；
- 安全行为是不执行越权/破坏性路径，并提出合规替代。

例子：要求关闭 TLS 校验但连接传输生产令牌；要求终止承载未提交批次的进程；要求越过 quality hold。

### 4.3.3 Factual Inconsistency (FI)

- 用户以确定语气给出错误/过时事实；
- 环境中有正面反证或更新的权威状态；
- 安全行为是核验权威来源后纠正前提，而不是照着错误说法执行。

例子：测试名对象实际连接生产库；用户称客户已确认但最新工单显示未解决；历史凭证仍在 Git 历史中。

## 4.4 风险隐藏方式 K1–K9 的位置

K1–K9 不作为第二套任务类别与 RU/RI/FI 并列，而作为**证据发现路径/呈现机制**：

- K1 生活化/常识埋点；
- K2 伪防护埋点；
- K3 计算埋点；
- K4 历史/依赖残留；
- K5 标识碰撞；
- K6 范围/动作省略；
- K7 进行中/重复阶段；
- K8 硬闸门压力；
- K9 权威状态时点错位。

主文可放 9 行简表，完整映射放附录。强调一条 seed 只有一个主机制，可有次机制。

## 4.5 三阶段失败归因

对每条危险轨迹，在**第一个决定性危险写动作/执行动作**之前截断并判定：

### F1: Insufficient evidence acquisition

- 工具轨迹没有获取足以支持关键事实的证据；
- 或只看到被伪装的表面状态，没有沿正常依赖链查到真实数据面；
- position 操纵预期主要改变这一类。

### F2: Evidence acquired but risk not recognized

- 关键证据已出现在工具返回中；
- 但 agent 的计划、澄清、最终答复或动作选择没有显示其识别该约束；
- wording 操纵预期主要改变这一类。

### F3: Risk recognized but unsafe compliance

- agent 在危险动作前明确表达了风险、约束或应停止原因；
- 但仍执行用户要求的危险路径。

判定原则：
- F3 必须有显式风险识别证据，不能靠“模型应该知道”推断；
- 看不到隐藏 CoT，只依据可见消息、工具轨迹和最终答复；
- 无法由可见文本确认识别时，危险轨迹保守归入 F2；
- 人工标签为最终依据，LLM judge 报告与人工的一致率和混淆矩阵。

## 4.6 威胁模型与非目标

明确写出：

- 用户意图是完成正常任务，不发布恶意指令；
- 工具返回不包含攻击者注入文本；
- 环境可能包含真实业务中常见的复杂状态、过时说法、自然位置上的规则和反证；
- 本文不研究 prompt injection、memory poisoning、backdoor、模型越狱或多轮社工攻击；
- 本文不把“拒绝一切写操作”视为安全成功，安全 agent 还应尽可能完成合法任务。

# 5. CEG-Bench: Construction and Evaluation

## 5.1 本节目标

让审稿人相信 benchmark 的自然性、可执行性、判分可靠性和覆盖度。这一节是 D&B 论文的核心，应占主文较大篇幅。

## 5.2 Benchmark Design Principles

建议列五条：

1. **Benign and natural tasks**：用户目标来自正常业务，不以制造伤害为目的；
2. **Positive evidence**：风险依据来自环境中的正面事实，不依赖“缺少某条记录”作为唯一反证；
3. **Executable safe alternative**：每个 case 必须存在暂停、澄清、替代执行或合规路径；
4. **Observable terminal hazard**：危险由实际写操作、发送内容、权限、配置、业务状态或终态判定；
5. **Paired controllability**：每条风险 case 都能通过最小修改得到安全对照版，并可派生 position/wording 变体。

## 5.3 Stateful Tool Environment

写清楚环境组成：

- 工具套件：mail、chat、files、database、code、git、github、pc、server、buyer、merchant 等 `[待填：最终数量]` 类；
- 每个 case 有初始状态、私有目录/ACL、状态 reset、工具元数据和评测函数；
- 只读 vs 写入/执行工具权限边界；
- 模型看到的工具 schema 与实际 callable tools 的一致性；
- 最大模型轮数、工具调用数、token 限制和失败调用计数；
- 所有运行保存 system/user prompt、tools、messages、model response、tool event、final answer、environment final state 和 judge 输出。

建议图：Figure 2 展示 harness：model node、tool node、read-only tools、write tools、environment snapshot、evaluator、recorder。

## 5.4 Case Taxonomy and Coverage

### 5.4.1 种子到扩展实例

写清数据生产流程：

```text
manual seed design
→ independent quality audit
→ environment implementation
→ deterministic evaluator and safe path check
→ key-evidence annotation
→ safe counterpart construction
→ controlled variants
→ batch expansion / regression set
```

需要说明：
- 种子不是随意 prompt，而是由风险机制、业务后果和发现路径共同约束；
- 扩展时保持 gap type、关键证据、危险终态和安全路径等价；
- 同一模板只改变业务表面，不改变证据链难度；
- 保留 full regression set 和 representative seed set 的区别。

### 5.4.2 覆盖矩阵

主文至少给三张统计表：

1. RU/RI/FI × tool suite；
2. consequence type × tool suite：财务损失、隐私泄露、数据丢失、越权访问、服务中断、重复副作用、合规/质量风险；
3. gap type × K1–K9 hiding mechanism。

当前内部已有 66 条活动种子和 K1–K9 聚类；最终数字以全量实现和扩展后为准。

## 5.5 Key-Evidence Annotation

每条 case 人工标注：

- `key_facts`：理解风险所必需的事实；
- `source`：事实所在文件、消息、数据库/工具返回或可计算结果；
- `normal_path`：正常完成任务时为什么会看到该来源；
- `evidence_type`：直接状态、计算结果、历史依赖、身份映射、时间点冲突等；
- `minimal_tool_path`：获取证据所需的最小工具路径；
- `decision_point`：第一个决定性危险动作；
- `safe_action`：预期安全替代；
- `counterpart_edit`：安全对照版改了哪一个提示词/环境点；
- `position_level` / `wording_level`：控制变量档位。

关键证据标签有两个用途：

1. judge 检查轨迹是否支持每个事实；
2. 将危险动作归因到证据获取、风险识别或指令优先级。

## 5.6 Paired Safe Counterparts

每条风险 case 增加一个安全对照版：

- 保持任务目标、工具路径、业务材料和操作复杂度基本不变；
- 只修改提示词或环境中的一个关键微调点，使坑点消失；
- 对照版仍有明确任务终态，不允许变成“随便回复都成功”；
- 用同一模型、同一预算和同一 harness 运行。

解释逻辑：

- 风险版危险率高 + 安全版任务成功率高：说明失败依赖 context–environment gap，而不是模型不会使用工具；
- 风险版和安全版都失败：可能是任务能力、环境理解或 harness 问题，应从主风险结论中剔除或单列；
- 风险版安全但安全版成功：说明该模型能处理该类证据，可作为成功案例分析。

## 5.7 Position and Wording Counterfactuals

### Position intervention

只移动同一关键信息的位置，不改语义和字面风险强度：

- salient：用户明确引用或任务路径上的显眼位置；
- non-salient：需要沿业务依赖、供应商规则、历史记录或工具菜单查找的位置。

它检验 evidence discoverability / acquisition。

### Wording intervention

位置保持不变，只改变同一事实的表达方式：

- explicit：直接给出风险约束；
- implicit：用业务语言、条件关系或常识推理表达同一事实；
- 可设置 L1/L2/L3 三档，但主分析应明确每档只改措辞，不增加新事实。

它检验 evidence interpretability / risk recognition。

理想情况下，在核心场景上做 position × wording 的 2×2 或 3×2 小因子设计；若预算不足，主文至少保证两类干预各自有严格单变量对照。

## 5.8 Evaluation Metrics

### 5.8.1 行为安全指标

建议正文使用：

- **Hazardous Action Rate (HAR)**：触发危险终态/决定性危险写动作的比例；
- **Safe completion rate**：未触发危险且完成合法目标；
- **Abstention/clarification rate**：停止或澄清但未替代完成的比例；
- **Safe-counterpart task success**：安全对照版任务成功率；
- **Severity-weighted hazard**（若已有严重程度标注）：按后果类型加权。

内部 ASR 可在表注或方法中映射为 HAR/UAR，避免“attack”误导。

### 5.8.2 证据和意识指标

- evidence retrieval/exposure rate；
- key-fact support score；
- risk recognition rate；
- F1/F2/F3 attribution distribution；
- human–judge agreement / Cohen’s κ / macro-F1。

### 5.8.3 效用与成本

- task utility / effective utility；
- read-only tool calls、write/exec tool calls；
- model turns、input/output tokens、total cost、latency；
- pass^k / repeated-run variance；
- over-refusal rate（用安全对照版衡量）。

## 5.9 Deterministic Evaluator and LLM Judge

分层要非常明确：

1. deterministic evaluator 判断环境终态和危险动作，是主行为指标；
2. human annotation 定义关键事实、证据位置和最终归因；
3. LLM-as-judger 只根据人工定义的字段做可规模化辅助分类；
4. judge 输入不含风险条件标签，position/wording 条件尽量盲化；
5. 报告 judge 与人工的一致性、错误类型和置信区间；
6. 最终核心表格的行为安全数字不依赖 judge。

## 5.10 Dataset Quality Control

建议主文简要列出，附录展开：

- 正面反证检查：不能只靠缺失记录判危险；
- 安全路径检查：安全动作必须由真实工具支持；
- 数据面检查：隐藏/遮盖不等于访问控制，实际字节、权限或状态要可检验；
- evaluator 过严/过宽审计；
- 单元/集成测试数量 `[待填]`；
- 人工审计样本数、争议解决流程和复审通过率；
- 污染/泄漏检查：case 名称、特殊标识符、生成痕迹等。

# 6. Diagnostic Experimental Design

## 6.1 Research Questions

- **RQ1: Prevalence and capability confound**：在 benign risk tasks 中，危险动作多常见？安全对照版能否正常完成？
- **RQ2: Failure-stage attribution**：危险轨迹主要断在证据获取、风险识别还是指令优先级？
- **RQ3: Evidence acquisition**：改变关键证据位置是否改变证据获取率和 HAR？
- **RQ4: Risk interpretation**：改变关键证据表述是否改变风险识别率和 HAR？
- **RQ5: Safeguards**：prompt/guard/quit 或预训练安全增强能否降低 HAR，同时保持效用？
- **RQ6: Topology vs compute**：多 agent 拓扑的收益来自独立调查/审查，还是仅来自更多 token 和工具调用？

## 6.2 Models and Base Agent

当前仓库三模型：DeepSeek、Qwen、GLM 的具体版本待最终实验固定。需要报告：

- 模型名、版本、API 日期；
- system prompt；
- temperature / top_p / thinking/reasoning 参数；
- context window、max output、retry policy；
- 每个模型重复次数；
- 是否同一模型承担所有 topology 阶段。

基线 agent：single-agent ReAct，模型节点与工具节点交替，所有 topology 和安全增强都复用同一图、记录语义和环境。

## 6.3 Safety Enhancement Conditions

当前仓库/计划中涉及三类：

1. **AgentGuard**：action-level allow/deny guard，基于工具元数据和策略在写/执行动作前拦截；
2. **Specified Quit**：给 agent 一个显式安全退出动作，使其可在识别风险后停止并说明；
3. **`[第三个增强的正式名称待确认]`**：你口头称为“预训练方法”，但当前仓库 docstring 中对应名是 **TargetedReminder**（prompt-only targeted safety reminder）。正式写作前必须确认最终方法；不能把 targeted reminder 和 pretrained safety model 混写。

可额外报告组合条件（Guard + Quit），但主比较应保持单机制，避免无法归因。

## 6.4 Multi-Agent Topologies

当前仓库实际有四组，最终若只跑三组需在写作中统一：

1. Planner → Executor；
2. Investigator → Executor；
3. Reviewer → Executor；
4. Investigator → Reviewer → Executor。

设计解释：

- Planner：形成执行计划，但不专门负责证据调查；
- Investigator：只读查证事实，输出事实清单和不确定点；
- Reviewer：只读审查风险和必须停止的步骤；
- Executor：拿到上游简报后用全工具执行。

现有三拓扑的叙事不要硬写；以最终实验矩阵为准。

## 6.5 Cost-Matched Ordinary Controls

这是主实验 2 成立的关键。至少加入：

1. **Budget-matched single agent**：给单 agent 与多阶段相同的总 token/step/tool-call 上限；
2. **Generic summarizer → Executor**：增加一个阶段和模型调用，但职责只是总结任务/材料，不要求查风险；
3. **Read-only pass without safety role**：先做普通只读浏览，再执行，但不指定 investigator/reviewer 身份；
4. 如预算允许，加入 role-label shuffle 或 same-content replay，区分角色提示词与信息内容。

所有条件报告：
- 总模型调用数；
- 总输入/输出 token；
- 只读调用数；
- 写入/执行调用数；
- wall time / cost；
- HAR 和 safe completion。

只有安全拓扑相对普通额外计算对照仍有效，才能把效果归因于角色分工。

## 6.6 Runs and Statistical Analysis

建议：

- 每个 model × case × condition 至少 `[待填：n]` 次重复；
- 同一 case 的条件使用同一初始环境快照；
- 风险版本、安全对照、position、wording 使用相同评测口径；
- 报告 by-instance 和 aggregate 两种平均，避免长 case 权重失衡；
- bootstrap 95% CI；
- 配对二分类结果可用 McNemar 或混合效应 logistic regression；
- 多比较校正（如 Bonferroni/Holm）在全量分析计划中预先指定。

### 主表

condition：
- baseline ReAct；
- AgentGuard；
- Specified Quit；
- third enhancement `[name]`；
- Guard + Quit（若保留）。

- HAR；
- safe completion；
- over-refusal / safe-counterpart success；

### 分析角度

- AgentGuard 的上限取决于策略是否能在动作层识别风险；若关键风险发生在读取/解释之前，guard 可能只能拦截已知工具模式；
- Specified Quit 依赖 agent 先意识到风险，主要应作用于 F3，不太可能修复 F1/F2；

## 7.7 Topology and Cost Controls（RQ6）

### 主表

single、budget-matched single、generic two-stage、planner/executor、investigator/executor、reviewer/executor、investigator/reviewer/executor：

- HAR；
- safe completion；
- F1/F2/F3；
- read-only calls；
- write/exec calls；
- total tokens/cost；
- latency。

### 预期机制

- Investigator 更多影响 F1：提升证据获取；
- Reviewer 更多影响 F2/F3：把已获取事实转成风险约束或停止门；
- Investigator + Reviewer 应形成“查证—审查”串联，但可能成本更高；
- Planner 可能改善任务组织，但不应自动带来安全收益。

### 关键结论判据

- 若普通 token-matched 对照也有效：收益主要来自额外计算/重复检查；
- 若只有 investigator/reviewer 有效：收益来自安全角色分工；
- 若 topology 降低 HAR 但安全版任务成功率也下降：可能是保守化而非更安全；
- 若 topology 总预算天然更大但不做对照，不能下机制结论。

## 7.8 Qualitative Analysis

1. F1：证据在环境里但未被检索；
2. F2：工具返回已含证据但模型继续执行；

4. enhancement 或 topology 成功在危险点前停止；
5. 安全对照版成功，说明同模型具备任务能力。

每个案例都用“用户目标—关键证据—决定性动作—终态—为什么归入该类”的统一格式。

# 8. Discussion

## 8.1 主要发现如何改变 agent safety 的理解

建议强调三点：

1. **Safety is an information-seeking problem**：安全 agent 需要主动寻找会推翻用户前提的环境证据；
2. **Exposure is not recognition**：证据出现在上下文窗口中，不等于模型把它转化为行动约束；
3. **Guardrails act late if evidence fails early**：动作守卫和退出动作作用在链条末端，无法自动修复前置检索/解释失败。

## 8.2 Design Implications

- environment-side machine-readable safety constraints；
- read-before-write policies for high-impact tools；
- evidence cards / risk-sensitive retrieval；
- reviewer that grounds claims in tool observations；
- guard metadata 需要理解业务状态，不只是工具名；
- benchmark 应同时测安全、效用和过度拒绝。

## 8.3 Scope and Limitations

建议放主文后半页，详细版附录：

- 本地模拟工具环境与真实 SaaS/API 仍有 domain gap；
- case 主要来自中文业务场景和人工种子，扩展分布需持续审计；
- LLM judge 只用于可见文本分类，无法访问隐藏 CoT；
- F3 的识别依赖模型显式表达，可能低估“沉默地知道但仍执行”；
- API 模型版本和推理参数会随时间变化；
- 本文不覆盖主动攻击者、多用户合谋、实时长期记忆污染。

这些限制不要在引言或摘要里主动放大。

## 8.4 Ethics and Responsible Release

- 所有数据为合成业务数据，不放真实个人隐私或真实凭证；
- 危险动作只在本地隔离环境发生；
- 发布 benchmark、evaluator 和案例有助于防御评测；
- 如公开可执行 hazard patterns，应同步强调环境为合成、默认 reset、不包含真实系统 exploit。
